## 一. 传统HTTP

![Image](assets/images/2f80f6d3a2/image-01.png)

自从1991年诞生以来，HTTP（超文本传输协议）便成为了互联网的通用语言。作为一种无状态，基于“请求-响应”模式的应用层协议，它构筑了现代WEB通信的基石。

在核心运作机制上，HTTP遵循着单向驱动的逻辑：通信必须由客户端发起request,服务器在处理完后返回完整的response。一旦数据传输完成，连接在逻辑上结束了。

但是随着web应用向"实时化"和高互动演化，传统的http暴露出了问题：

- 无法主动推送

- 头部开销过大

- 实时性的伪实现：为了模拟事实性，传统http只能用轮询，不管是长轮询还是短轮询，都会产生大量的冗余请求



## 二. 流式HTTP（Streamable HTTP）

![Image](assets/images/2f80f6d3a2/image-02.png)

流式http打破了传统http的一个request和一个response,而是边计算边传输。

流式http的精髓在于不是一次性交付完所有数据，而是通过特定的协议头，将数据化整为零。

- 传输机制：在http响应头中声明`Transfer-Encoding: chunked`（分块传输编码）或 `Content-Type: text/event-stream`。这告诉客户端：服务器目前不清楚响应的总长度，但是会将数据切分成一个一个trunks依次下发

- 客户端在收到 200 OK 的状态码时，并不会立刻中断TCP连接。借助现代浏览器的 Fetch API 及其 `ReadableStream` 特性，前端可以像接水管一样，源源不断地处理服务器发来的数据块，直到服务器发送一个长度为0 的终止信号。

这种边读边传的特性，在以下场景中应用广泛：

- 大模型的前端的打字机显示效果：目前ChatGPT、Claude 等模型生成的长文本，正是通过流式 HTTP 将响应数据实时推送到前端，显著降低了用户的首字感知延迟（TTFT）。避免用户等待大模型一次返回所有响应内容，视觉效果差。

- 大容量资源下发：超大文件或者视频流分段加载，避免内存爆炸，提高系统吞吐量

- 灵活替代SSE：配合fetch-event-source等库，能够完美模拟SSE的长连接，同时避免了标准SSE的只能GET请求和自定义header的请求。

虽然流式传输在逻辑上很美好，但在工程落地时必须关注“链路通畅”问题：

- 单向传输局限：本质上仍然是server-to-client单向数据流，如果业务需要客户端回传到服务端，需要考虑其他通信协议

- 代理服务：一些旧版的Nginx,负载均衡器等默认开启了强缓冲（Buffering），这导致了它们会试图"积攒"足够多的流式数据再统一发给客户端。需要确保代理层配置了`X-Accel-Buffering: no`保证禁用强缓冲。



## 三. SSE（Server-Sent Events）

![Image](assets/images/2f80f6d3a2/image-03.png)

如果说 流式 HTTP 是一种底层的“传输机制”，那么 SSE 则是基于此机制建立的一套标准化应用层协议。

SSE不允许像普通流那样随心所欲的传输字符，强制响应头设置为 Content-Type: text/event-stream，且数据格式必须遵循一套严密的报文规范：

- 结构化字段：每条消息由id:，event：（事件类型），data：（业务数据）和retry：（重连间隔）等字段组成。

- 消息边界：必须以\n\n作为一条独立消息的终点，这种协议级别的约定使得客户端能够精准拆解每一条业务事件。

SSE的一大优势是深度集成了浏览器原生的`EventSource API`。这赋予了SSE许多开箱即用的特性：

- 自动重连：当网络波动导致连接中断时，EventSource会自动发起重连尝试

- 状态追踪：利用 Last-Event-ID机制，客户端在重连时会自动携带最后一次收到的ID，服务端可以实现数据的断点续传，确保信息不丢失

SSE非常适合那些“高频下发，低频上报”的业务场景，比如金融行情，状态监控等。尽管SSE足够轻巧，但是实际架构设计中，必须正视其局限性：

- 文本编码限制：SSE仅支持UTF-8文本流，如果需要传输二进制文件，必须先转码成base64，这会带来33%的开销。

- 浏览器限制：原生的EventSource只支持“GET”请求。

## 四. WebSocket

![Image](assets/images/2f80f6d3a2/image-04.png)

websocket是跳出了http传统框架的一次新的革命，它是一个和http平级的应用层协议。

它是一种基于TCP协议的全双工通信协议，客户端和服务器可以双向，实时，低延迟地传输数据，链接全程保持开放。

websocket的建立遵循一个标准化的协议升级流程：

- 协议升级握手：连接初始化阶段采用标准的HTTP请求。客户端在请求头中声明 `Upgrade：websocket`与 `Connection：Upgrade`，表明协议的升级意图。

- 连接状态转换：服务器确认支持websocket协议后，返回 101 Switching Protocols 状态码，底层TCP连接完成协议转换，后续通信采取 websocket帧格式进行数据传输，客户端和服务器可以随时、独立地向对方发数据，无需等待对方请求或者确认。

除此之外，websocket还具有以下优势：

- 轻量级的帧结构：websocket的数据帧首部极其紧凑，固定部分仅有两字节，带掩码的最大14字节。

- 原生二进制支持：websocket协议原生支持utf-8和二进制数据帧，不需要向SSE那样需要进行base64编码转换。该特性使得websocket在音视频流传输等多媒体场景优势显著。

同时，作为一种“有状态的协议”，websocket在带来极致性能的同时，也给后端架构带来了沉重的复杂性：

- 状态维护与内存开销：服务器必须为每一个websocket维持一个持久的session状态。当并发量攀升到十万甚至百万级别时候，内存占用对服务器压力很大

- 分布式系统的挑战：因为连接具有状态属性，如果用户A连接到机器1，一用户B连接到机器2，这二者之间的通信无法直接完成。后端必须引入redis Pub/sub，消息队列或者专用网关等中间件，以实现跨节点的消息对齐与状态同步。

- 原始协议的局限：websocket本身设计的极为精简，没有内置自动重连，心跳保活或者消息确认机制。开发者必须自行实现上述机制。

## 五. Webhooks

![Image](assets/images/2f80f6d3a2/image-05.png)

webhooks是服务器主动推送给服务端，是一种基于HTTP的事件触发机制，专门为服务器向服务端单向推送而设计。

webhooks的工作模式非常清晰：

客户端预先在服务端注册一个回调URL，并且指定关注的事件类型。当服务端发生指定事件时候，它会向客户端注册的URL发送一个HTTP POST请求，将事件详情封装在请求体中。客户端收到回调时，执行相应的业务逻辑，并返回一个确认响应。

整个过程完全基于HTTP，无需维护持久连接，也无需客户端持续轮询。

webhooks的特性决定了它非常适合跨系统的场景：

- 支付回调：用户在第三方平台完成付款后，支付平台会向商户服务器发送webhook回调，通知交易结果

- 版本控制系统：github等平台通过webhooks在代码提交、PR提交时候通知外部的CI/CD系统

虽然webhooks的概念简单，但是在生产环境中需要关注几个关键问题：

- 可靠性：HTTP请求可能因为网络问题投递失败，因此主流平台通常支持失败重试机制，并且要求回调端点返回2xx状态码才是视为成功。

- 幂等性设计：由于重试机制的存在，同一个事件可能被多次投递，客户端应当具备幂等处理能力，避免重复业务操作。

- 安全验证：为了防止恶意伪造回调，服务端通常会在请求中加入签名（比如HMAC签名），客户端通过验证签名来确认请求的真实性。



## 六. 一些思考与讨论

HTTP轮询是一种最朴素的实时通信方案，核心逻辑设计客户端定时向服务器发起请求，主动拉取最新数据。通信协议没有高低优劣之分，只有在不同的场景中是否合适之分。

以AI应用业务场景为例：

|应用类型|场景特征|解释说明|
|---|---|---|
|文本大模型|流式持续输出|模型在极短时间内就开始返回数据，随后持续“吐字”。如果采用传统HTTP，用户将面临长达数秒的白屏等待，因此SSE/流式HTTP适合此场景|
|AI生图/生视频|重计算异步任务|一张高质量图片的生成需要GPU满载运算10到30秒，甚至在高峰时间需要排队数分钟。在生图期间，除了偶尔的生成进度更新，并没有持续的数据流可控传输。让客户端和网关之间维持一条长达数十秒的闲置长连接收益不大。<br>- 大多数云厂商的负载均衡器CDN（内容分发网络）对HTTP连接有严格超时限制，当ai任务耗时过长，网关会自切断链接<br>- 服务器的并发连接池是有限的。|

现代高并发AI生图平台的后端架构通常是彻底解耦的：

1. 提交任务（client）：客户端 POST请求 `/api/generate`

2. 下发队列（API Server）：API服务器将任务投入 `Kafka/RabbitMQ` 队列中，生成唯一 `task_id` 并且立即返回给客户端

3. 异步消费（GPU Worker）：后端GPU节点从队列中取出任务，执行计算。生成完毕后，将图片上传至 `OSS/S3`并将结果写入数据库

4. 获取结果（client）：客户端持有 `task_id`，每隔数秒轮询一次 `/api/task/{tasl_id}` 查询任务状态

在这个例子中，处理HTTP请求的web服务器与真正执行计算的GPU服务器在物理上是隔离的。不能使用websocket或者SSE强制将二者串联。

除此之外，在弱通信环境下（地铁高铁），用户在这类场景中使用手机生图，刚提交任务遭遇了五秒的网络中断：

- 如果使用websocket：连接断开后，由于websocket协议简单，因此需要一套复杂的重传与回话恢复机制

- 如果使用轮询（polling）：客户端持有 `task_id`。网络恢复后，继续发送 `GET/api/task/{task_id}` 即可获得结果。无状态特性带来了强干扰能力。

当然，如果决定采用了polling，需要兼顾体验和服务器压力，业界通常会采用退避轮询策略——随着任务等待时间延长，逐步降低查询频率。

## 七. 实践选型指南

**在实际应用中，脱离业务场景谈协议与通信方案的优劣是毫无意义的。**

决策矩阵：

|业务场景|任务耗时特征|推荐通信协议|决策依据和变通方案|
|---|---|---|---|
|AI文本对话|快速响应，持续文本流|流式HTTP|需要提供打字机反馈以维护用户注意力。相比websocket，http更衣穿透防火墙与网关|
|AI实时语音|极低延迟，双向高频互动|websocket|需要消除HTTP握手和头部延迟|
|AI快速生图|耗时极短，无排队压力|标准HTTP|简单的挂起等待即可|
|高精度生图/视频生成|耗时长且需要排队|异步提交+HTTP轮询|解耦GPU计算节点和web节点，客户端持task_id定时查询状态|
|跨系统时间同步|事件驱动，无固定耗时|webhooks|适用于服务端之间的异步事件通知。接收方需要提前暴露回调URL，并确保幂等处理与签名验证|

真正成熟的架构师，不会执着于最新或者最复杂的方案，而是深入理解每种技术的边界与代价，在业务场景的约束下做出优雅地取舍。毕竟，最好的架构不是用技术堆砌出来的，而是让技术各归其位。
