# Deferred MCP Tools（261027）

Deferred MCP Tools（延迟加载的 MCP 工具）是一种将工具可见性与可调用性分离的上下文管理策略：模型默认只看到工具名或极简描述，完整 Schema 仅在任务需要时通过搜索或发现流程动态注入。它的核心价值不在于单纯节省 Token，而在于让 Agent 在连接数百甚至上千个工具时，不会因为上下文被无关定义塞满而丧失判断力。

然而，2026 年的一项生产环境研究揭示了一个被广泛忽视的失效模式：当工具名称与用户任务措辞在词汇上不重叠时，搜索几乎无法找回正确工具。在 26 个真实工具的测试中，词汇对齐时 Recall@1 为 100%，词汇不对齐时骤降至 7.69%，且扩大搜索窗口到 Top 5 仅多找回 1 个工具。这一失败与语料规模无关——从 26 个工具到 300 个工具，不对齐场景的 Recall@5 始终停留在 11.54%。

因此，一个完整的 Deferred MCP Tools 方案必须同时回答两个问题：如何省 Token，以及如何确保该被找到的工具真的能被找到。

## 一、为什么需要 Deferred MCP Tools

### 1.1 预加载的隐性成本

每个 MCP 工具的完整 Schema 包含名称、描述、输入参数结构、可选的输出结构，平均消耗 150–400 个 Token。当一个 Agent 接入 GitHub、Slack、数据库、内部服务等 5 个以上 MCP Server 时，工具定义总量轻易达到 60–100 个，仅 Schema 就可能占据上下文窗口的 15%–20%。

更隐蔽的代价在于注意力稀释。TrueFoundry 的分析指出，工具定义的重复成本会导致注意力竞争（候选越多选择越难）。 当模型面对数十个语义相近的工具描述时，选错工具不会报错——它只是安静地选了一个“看起来合理”的错误选项。

### 1.2 延迟加载的核心思想

TrueFoundry 将这一策略表述为一句简洁的原则：“让目录可达，但不让目录永久在场。” 连接工具服务器回答的是“运行时能触达哪些能力”，而加载工具定义回答的是“模型在这一步必须考虑哪些描述与 Schema”。 Deferred Loading 把这两个问题拆开：启动时只暴露 Server 名称和极简工具列表，完整定义在需要时再取。

Anthropic 的工程实践报告了该策略的量化效果：在一项代表性任务中，工具相关上下文从约 150,000 Token 降至约 2,000 Token，降幅 98.7%。这一数字常被引用为延迟加载的“卖点”，但它掩盖了一个前提假设：模型知道该搜什么。



## 二、Deferred MCP Tools 的运作机制

### 2.1 基本发现循环

以 TrueForge 的文档化实现为例，当预加载关闭时，系统用四个元工具替代所有个体工具定义。模型首次需要使用某个工具时，经历一个短规划循环：识别相关 Server → 列出其工具 → 查看候选工具 → 调用。

一个更简化的自建实现模式如下：

1. 起始状态只激活 `search_tools`：Agent 无法调用其他任何工具。

2. Agent 发出搜索：查询与当前需求相关的关键词。

3. 工具激活：系统将匹配的工具名称载入活跃集合，并在下一轮对话中提供其完整 Schema。

4. Agent 使用工具：调用已加载的工具完成任务。

5. 会话结束卸载：下次请求从干净状态开始。

### 2.2 选择性预加载：务实的中间道路

全有或全无的选择在实践中很少最优。TrueForge 的配置支持对一个 Server 保持延迟加载，同时预加载指定的高频工具。例如，GitHub Server 整体延迟，但 `search_pull_requests` 始终可见，因为它在几乎每次交互中都会被用到。

判断是否预加载不应只看工具数量。一个 100 工具但每月只用一次的 Server 应保持延迟；一个 30 工具中两个读操作每次运行都出现的 Server 则值得选择性预加载。核心单位是重复上下文成本 × 实际使用频率。

### 2.3 与 Prompt Caching 的冲突

延迟加载与大多数提供商的 Prompt 缓存机制存在张力：在对话中途增删工具定义会使缓存前缀失效，缓存未命中的代价可能超过省下的定义 Token。MCP 官方客户端最佳实践建议：将新发现的定义追加在缓存断点之后而非重新排序 `tools` 数组，或通过一个稳定的 `call_tool({name, args})` 元工具路由所有调用，使数组永不变化。

## 结语

Deferred MCP Tools 解决的是一个真实且日益紧迫的问题：当 Agent 接入的工具目录从几十膨胀到上千，全量预加载会同时吞噬上下文预算和选择准确性。Anthropic 报告的 98.7% Token 削减是真实的，TrueForge 的选择性预加载配置也是可落地的。

但 ThakiCloud 的研究提醒我们，延迟加载的收益是有条件的。条件就是：Agent 必须能够用它自己的语言，找到那个它甚至不知道存在的工具。当工具名称与任务措辞之间隔着一条词汇的鸿沟时，搜索不会报错，不会降级，它只是安静地返回无关结果，然后 Agent 退回到手工 grep 或更笨拙的替代方案。一个无法被找到的工具，在功能上等于不存在。

因此，完整的 Deferred MCP Tools 策略不是“打开延迟加载开关”就结束的。它需要预加载判据的离线验证、描述层的词汇工程、以及选择性预加载的精细配置三者配合。省 Token 是起点，找得到才是终点。
