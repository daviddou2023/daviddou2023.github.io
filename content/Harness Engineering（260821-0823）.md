## 一、引言

---

一个团队用 Claude Sonnet 给一个中等规模的 Python Web 应用（FastAPI + PostgreSQL + Redis，约 15,000 行代码）添加新的 API 端点。

起初他们只给了一句话："在 `/api/v2/users` 下添加用户偏好设置端点"。结果呢？agent 花了 40% 的上下文窗口探索仓库结构，产出了看似合理的代码但没遵循项目的错误处理模式，用了旧版 SQLAlchemy 语法，宣称完成但端点实际有运行时错误。下一个会话还得重新做发现工作。

后来他们加了 `AGENTS.md`（描述项目架构和技术栈版本）、显式的验证命令（`pytest tests/api/v2/ && python -m mypy src/`）、和架构决策记录。同一模型在三次独立运行中全部成功，上下文使用效率提高了约 60%。

模型没变。变的是除了模型之外的那些东西。

过去两年，我们一直在争论模型。哪个模型最智能？哪个模型的性能最好？哪个模型产生的幻觉最少？这种讨论本身无可厚非，但它忽略了系统的另一半。模型只是运行中的agent的一个输入。

> **The rest is the *****harness*****: the prompts, tools, context policies, hooks, sandboxes, subagents, feedback loops, and recovery paths**** wrapped around the model so it can actually finish something.**
> 
>

### 1、Agent = Model + Harness

---

Viv Trivedy 提出了“Harness Engineering”这个术语（https://x.com/Vtrivedy10/status/2031408954517971368），它的一句话涵盖了什么是harness？

---

> **Agent = Model + Harness**
> 
> **If you're not the model, you're the harness.**
> 
> 

---

Harness是指除模型本身之外的所有代码、配置和执行逻辑。一个原始的模型本身并不算作一个智能体。但当harness为它提供诸如状态管理、工具执行、反馈机制以及可强制执行的约束条件时，它才真正成为一个智能体。

![Image](assets/images/e5279e9b4e/image-01.png)

具体而言，harness包括：

- 系统提示`CLAUDE.md`、`AGENTS.md`技能文件和子代理提示

- 工具、技能、MCP 服务器及其描述

- 捆绑式基础设施（文件系统、沙箱、浏览器）

- 编排逻辑（子代理生成、交接、模型路由）

- 用于确定性执行的钩子和中间件（压缩、延续、代码检查）

- 可观测性（日志、追踪、成本和延迟计量）



工程师们总是会陷入这样的陷阱。Agent出了些问题，工程师就责怪模型，而所有的责任都被推到“等待下一个新模型版本”上。但是这似乎是避重就轻地逃避了问题。根据viv的Agent等式“agent = model + harness”，model的性能提升确实会提升agent能力，但是使用现有模型，提高harness设计，亦可以使agent性能提升。

一个性能优良的模型搭配一个出色的harness，胜过一个性能优异的模型搭配一个糟糕的harness。越来越有趣的工程设计不在于选择模型，而在于围绕模型设计harness。

通过harness engineering的思维分析，agent出现的问题所对应的解决办法是显而易见的。比如，agent没有了解某个约定，所以你需要添加相应的注释来说明这一点；agent执行了有破坏性的命令，所以你需要添加一个hook来拦截这个命令的执行；agent在复杂的任务中迷失了方向，所以你需要将任务拆分成多个子任务，分别由不同的模块来处理；agent不断“修复”那些有缺陷的代码，所以你需要在循环中加入类型检查功能，以产生反馈信号来指导agent行为。

在 Viv 的报告中以及 HumanLayer 的研究中，都有一个显著的现象值得注意。在 Terminal Bench 2.0 环境下，使用 Claude Code 框架运行的 Claude Opus 4.6 模型的得分，远低于使用自定义训练集运行的同一模型。Viv 的团队仅通过修改训练集，就将coding agent的排名从前 30 位提升到了前 5 位。将模型切换到不同的训练集，使用更高效的工具、更精确的提示语，以及更强的反向强化机制，可以充分发挥原始训练集所不具备的能力。这佐证了harness的能力体现。

---

> **HumanLayer says: *****“it’s not a model problem. It’s a configuration problem.”***** Harness engineering is what happens when you take that seriously.**
> 
> 

---

好的harness不比model差。

### 2、Harness的系统组成

---

![Image](assets/images/e5279e9b4e/image-02.png)

- 指令子系统：创建 `AGENTS.md`（或 `CLAUDE.md`），内容包括项目概览和目的、技术栈和版本、首次运行命令、不可违反的硬约束、指向更详细文档的链接。

- 工具子系统：确保 agent 有足够的工具访问权限。

- 环境子系统：让环境状态自描述。用 `pyproject.toml` 或 `package.json` 锁定依赖，用 `.nvmrc` 或 `.python-version` 指定运行时版本，用 Docker 或 devcontainer 让环境可重现。

- 状态子系统：长任务必须有进度跟踪。用一个简单的 `PROGRESS.md` 文件记录：哪些做完了，哪些在做，哪些被阻塞。每个会话结束前更新，下一个会话开始时读取。

- 反馈子系统：这是投入产出比最高的子系统。

量化 harness 组件价值的方法：用"控制变量排除法"。保持模型不变，逐个移除五个子系统，看哪个子系统缺失时性能下降最多。下降最多的组件，说明它在当前任务里边际贡献最大，值得优先保留；是否要加强它，取决于失败归因，而不是只看下降幅度

### 3、Making the Repository the Single Source of Truth

---

仓库配置的原则：

- 原则 1：知识靠近代码。 一条关于 API 端点认证的规则，应该放在 API 代码旁边，而不是藏在一个巨大的全局文档里。每个模块目录下放一个简短的文档，说清楚这个模块的职责、接口和特殊约束。模块目录本身就是天然的索引，agent 读到代码就能读到约束，不用到处翻找。

- 原则 2：用标准化的入口文件。 `AGENTS.md`不需要包含所有信息，但必须能让 agent 快速回答"这是什么项目"、"怎么跑"、"怎么验证"这三个问题。50-100 行就够了。

- 原则 3：最小但完备。 每条知识都应该有明确的使用场景，刚好够用。如果你删掉某条规则不影响 agent 的决策质量，那这条规则就不应该存在。

- 原则 4：和代码一起更新。 把知识更新跟代码变更绑定在一起。最简单的方法：把架构文档放在对应的模块目录里。改代码的时候自然会看到文档，改代码之后 CI 提醒你检查文档是否需要更新。

具体的仓库结构：

```Python
project/
├── AGENTS.md              # 入口：项目概览、运行命令、硬约束
├── src/
│   ├── api/
│   │   ├── ARCHITECTURE.md  # API 层的架构决策
│   │   └── ...
│   ├── db/
│   │   ├── CONSTRAINTS.md   # 数据库操作的硬约束
│   │   └── ...
│   └── ...
├── PROGRESS.md             # 当前进度：做了什么、在做什么、被什么阻塞
└── Makefile                # 标准化的操作命令：setup、test、lint、check
```

### 4、The ratchet: every mistake becomes a rule

---

在harness engineering，最重要的习惯就是把agent的错误变成一个习得的规则。

每当Agent犯下某个错误时，开发者不能仅仅在当前的对话里纠正它，而必须花时间把这个教训固化为系统、环境或文档中的一条硬性规则。就像ratchet一样，只许前进不许后退——系统会随着错误不断增加约束，变得越来越严密，从而确保同样的错误永远不再发生。这和人类“一朝被蛇咬十年怕井绳”的道理类似。

## 二、Working Backwards from Desired Agent Behavior to Harness Engineering

---

![Image](assets/images/e5279e9b4e/image-03.png)

---

> **Behavior we want (or want to fix) → Harness Design to help the model achieve this.**
> 
> 

---

我们希望实现的行为→（逆推）→ 设计相应的工具来辅助模型达成这一目标。

![Image](assets/images/e5279e9b4e/image-04.png)

采用这种设计方式的优点在于，每个组件都有明确的职责。如果你无法为某个组件的功能命名，那么很可能这个组件属于冗余部分，就不应该存在。

本节的其余部分按照 Viv 的讲解顺序来逐步介绍这些内容，其中有一些特定的模式值得学习。

### 1、Filesystems for Durable Storage and Context Management

我们希望agent能够拥有持久的存储能力，以便与真实数据进行交互；能够处理那些不适合特定上下文的信息；并且能够跨会话保存工作成果。

模型只能在其上下文窗口内的知识上进行操作。在文件系统出现之前，用户必须直接将内容复制/粘贴到模型中，这种操作方式非常繁琐，也不适合agent。

---

> **Harnesses ship with filesystem abstractions and tools for fs-ops.**
> 
> 

---

利用文件系统抽象层以及用于文件操作的工具来实现驱动程序：

- Agents拥有一个工作区，用于在其中读取数据、编写代码以及查看相关文档。

- 工作可以逐步添加并卸载，而不是将所有内容都保存在同一个上下文中。Agent可以存储中间结果，并且其状态可以持续存在，即使会话结束之后也不会消失。

- 文件系统是一种天然的协作平台。多个Agent以及人类可以通过共享文件来进行协作。

- Git 为文件系统增加了版本控制功能，这样一来，各个Agent就可以跟踪工作进展、回退错误，以及进行分支实验。

在写AGENTS.md这类文档时，不是写越多越好，而是"把重要信息放到正确的位置"的问题。一份在 `src/api/` 目录下、50 行的 `ARCHITECTURE.md`，比一份在 Confluence 里、500 页但没人维护的设计文档有用得多。就近放置的价值远大于篇幅长短，因为信息只有在你需要的时候就在手边，才能真正发挥作用。

![Image](assets/images/e5279e9b4e/image-05.png)

怎么检验你的仓库配置的够不够好？开一个全新的 agent 会话，只让它看仓库内容，看它能不能回答五个基本问题。

如果它答不上来，说明配置有空白。空白的地方，agent 就得自己猜，猜错了就是 bug，猜多了就浪费上下文。每个新会话都要猜一遍，猜的成本远高于一开始就把仓库配好。

![Image](assets/images/e5279e9b4e/image-06.png)

### 2、Bash + Code as a General Purpose Tool

---

我们希望代理能够自主解决问题，而无需人类预先设计每一种工具。

如今，智能体执行的主要模式是 ReAct 循环。在这种模式下，智能体先进行推理（reasoning），然后通过调用工具来执行某个动作（action），接着观察结果（Obeservation），最后在一段时间内重复这一过程。不过，智能体只能执行那些有相关逻辑的工具。与其让用户为每一种可能的Action都构建相应的工具，更好的解决方案是给智能体提供像 bash 这样的通用工具

---

> **Harnesses ship with a bash tool so models can solve problems ****autonomously by writing \& executing code.**
> 
> 

---

“Bash + code”是一种重要的创新，它极大地扩展了模型的功能边界，让模型能够即时通过代码创建自己的工具，而不需要受到固定预配置工具的约束，从而能够自主地解决相关问题。

---

### 3、Sandboxes and Tools to Execute \& Verify Work

---

在本地运行由agent生成的代码存在风险，而单个本地环境也无法处理大型代理工作负载。Agents需要有一个相对安全且适配的环境，这样它们才能安心地执行任务、观察结果并取得进步。

沙箱（sandbox）为代理提供了安全隔离的工作环境。与在本地执行相比，这些沙箱可以让测试工具连接到沙箱中进行代码运行、文件检查、依赖项安装以及任务完成。

为了进一步提高安全性，测试工具可以允许某些命令执行，并强制实施网络隔离。此外，沙箱还支持按需创建多个环境，这些环境可以分散应用到多个任务上，而完成任务后也可以轻松地删除这些环境。

诸如浏览器、日志查看工具、屏幕截图以及测试运行器等工具，为代理程序提供了观察和分析工作的手段。这帮助他们能够创建自我验证机制，从而编写应用程序代码、运行测试、检查日志并修复错误。安装配置这些工具也是harness的范畴，从而让agent能够将精力集中在处理业务上。

### 4、Memory \& Search for Continual Learning

---

agents应该记住他们所学到的知识，并且能够访问在训练时没接触过的信息。

模型仅拥有它们的权重信息，以及当前所处的上下文环境。由于无法编辑模型的权重，因此给模型加外挂的唯一方式就是通过注入上下文信息（context injection）。

在内存方面，Harness 支持像 AGENTS.md 这样的内存文件格式，这些文件在agent启动时会被注入到上下文中。当agent添加或编辑这些文件时，Harness 会将这些更新后的文件加载到上下文中。这是一种持续学习（continual learning）的方式，代理能够持久保存某次会话中的知识，并将这些知识应用到后续的会话中。

模型无法直接访问本身知识库形成之后的新数据，比如更新后的库版本等信息。为了获取最新的知识，网络搜索和 MCP 工具如 Context7 可以帮助代理访问那些超出知识截止点范围的信息，比如新的库版本或训练结束时不存在的当前数据。

---

### 5、Battling Context Rot

---

上下文的恶化描述了当模型的应用上下文窗口不断填充时，其推理能力和任务完成能力反而下降。上下文是一种珍贵而稀缺的资源，因此需要相应的策略来管理它。



> **Harnesses today are largely delivery ****mechanisms for good context engineering****.**
> 
> 

- Compaction 功能解决了当上下文窗口接近填满时的问题。通过智能的压缩操作，可以卸载并汇总现有的上下文信息，从而让agent能够继续正常工作。

- Tool calling offloading 功能有助于减少大量工具输出对上下文窗口的影响，因为这些输出可能会产生噪音，并占用不必要的资源。该机制会保留工具输出的头部和尾部信息，当这些信息的数量超过一定阈值时，系统会将完整的输出结果卸载到文件系统中，这样模型在需要时可以访问这些结果。

- Skills 用于解决这样一个问题：智能代理启动时，上下文中会加载过多工具或 MCP 服务，导致代理还没开始工作，性能就已经受损。 Skills 属于框架层的基础原语，它通过渐进式暴露（progressive disclosure）的机制来解决该问题。 并非模型主动选择在启动阶段就把 Skills 的前置元信息（名称和一句话描述）加载进上下文；而是框架层面可以提供该能力，以此保护模型免受上下文膨胀退化的影响。

### 6、Long Horizon Autonomous Execution

---

我们希望代理能够在长期的时间内，自主地、正确地完成复杂的任务。

目前的模型存在诸如过早终止、无法分解复杂问题以及在不同上下文窗口中无法保持连贯性的问题。一个好的框架设计必须考虑到所有这些问题：

- 借助文件系统与 Git 可跨会话留存进度：文件系统持久存储代理产生的海量任务数据；Git 便于代理快速掌握项目历史与最新状态；同时文件系统可作为多代理协作的共享工作记录载体。

- Ralph Loops 保障任务持续推进：该约束模式依靠钩子拦截模型退出行为，把原始提示重新注入新上下文，强制agent接续工作；依托文件系统读取上一轮状态，实现在全新上下文下迭代任务。

- 规划与自我验证保障目标落地：规划把大目标拆解为分步任务，由运行框架通过提示、计划文件辅助完成，每步完成后agent开展自检。

### `7、AGENTS.md` Design

---

AGENTS.md文件在每一轮操作中都会出现在系统提示中。有两条宝贵的经验值得注意：

- 请保持文字简洁。HumanLayer 团队将他们的作品控制在 60 行以内。每一行都在争夺读者的注意力，而更多的规则只会让每条规则变得不那么重要。这是一份操作清单，而不是风格指南。

- 每一行都需要有合理的理由。这些规则应该源于某个具体的过去失败事件，或者某种严格的外部限制。否则，这些规则就只是无意义的噪音而已。采用棘轮机制来制定规则吧——不要进行无意义的头脑风暴了。

但是需要预防将到的所有规则、约束、历史教训都塞进去，把AGENT.md构建成一个臃肿重复的文件。每次出问题就在AGENT.md这似乎是很符合直觉的事情，但是所造成的累积效应是灾难性的。

- 上下文预算被吃掉了。 Agent 的上下文窗口是有限的。假设你的 agent 有 200K tokens 的窗口，一个膨胀的指令文件可能占掉 10-20K。看起来还有不少余量？但一个复杂的任务可能需要读几十个源文件，工具执行的输出也占上下文，对话历史也在累积。到真正需要理解代码的时候，预算已经不够了。

- 中间迷失。 "Lost in the Middle"这篇论文（Liu et al., 2023）清楚地证明了：LLM 对长文本中间部分的信息利用效率显著低于两端。你的 AGENTS.md 有 600 行，如果你把一项重要的规则写在了300行左右中间的位置，agent 几乎一定会忽略它。

- 优先级冲突。 文件里混合了不可违反的硬约束、和某个特定场景的历史教训。这些规则的重要性完全不同，但在文件里看起来一模一样。Agent 没有可靠的信号来区分哪个是红线，哪个只是建议。

- 维护衰减。 大文件天生难维护。指令过时了没人删，因为删除的后果不确定，但加新指令是无成本的。结果文件只增不减。

- 矛盾累积。 不同时期加的指令之间开始出现矛盾：一条说"用 TypeScript 严格模式"，另一条说"某些遗留文件允许用 any"。Agent 每次随机选一条遵循。



解决思路是进行拆分：常用信息放手边，偶尔用的收起来，用不上的别带。

入口文件 `AGENTS.md` 控制在 50-200 行，只放最常用的东西：项目概览、首次运行命令）、全局硬约束）、指向专题文档的链接。

```Markdown
# AGENTS.md

## 项目概览
Python 3.11 FastAPI 后端，PostgreSQL 15 数据库。

## 快速开始
- 安装：`make setup`
- 测试：`make test`
- 完整验证：`make check`

## 硬约束
- 所有 API 必须走 OAuth 2.0 认证
- 所有数据库查询必须用 SQLAlchemy 2.0 语法
- 所有 PR 必须通过 pytest + mypy --strict + ruff check

## 专题文档
- API 设计规范 (`docs/api-patterns.md`) — 添加新端点时必读
- 数据库操作约束 (`docs/database-rules.md`) — 涉及数据库修改时必读
- 测试标准 (`docs/testing-standards.md`) — 编写测试时参考
```

每条指令都应该标明来源、适用条件、过期条件。定期审计，删掉过时的、冗余的、矛盾的条目。

如果某条指令必须在入口文件里，放顶部或底部，不要放中间。但更好的做法是把指令放到专题文档里，让 agent 按需加载。

OpenAI 和 Anthropic 都隐性支持拆分的做法。OpenAI 说入口文件应"短小且以路由为导向"，Anthropic 说长运行 agent 的控制信息应"简洁且高优先级"。两家都在说同一件事：别把什么都塞进一个文件里。

## 三、harness engineering 实践经验

---

### 1、用 ACID 原则管理 agent 状态

这个类比来自数据库的事务管理。虽然看起来比较复杂，但它确实提供了一个非常实用的框架：

- 原子性：每次"逻辑操作"用一个 git commit 原子化。中途挂了就 `git stash` 回滚。

- 一致性：定义状态词确保一致，比如所有测试通过、lint 无报错。Agent 每次操作后跑验证，不一致的中间状态不要 commit。

- 隔离性：多个 agent 并发工作时，状态文件要避免竞争条件。简单方案：每个 agent 用独立的进度文件，或者用 git 分支隔离。

- 持久性：关键的项目知识用 git 跟踪的文件持久化。临时状态可以只在会话内存里，但跨会话必须的知识必须写到文件里。

### 2、让跨会话的任务保持上下文连续

---

在agent实际工作时候，会遇到这样的问题，在当前对话已经做了大部分工作，但是当前对话上下文满了，只能再开一个新对话继续，然后发现agent不记得上次做了什么决策了，哪些文件已经改过，进行到什么状态了。它得花 15 分钟重新探索一遍项目，而且可能跟上次的做法不一致。这就是agent在跨对话任务中“断片”的现象。

出现这种现象的直觉原因是上下文窗口是有限的。这不是一个可以通过模型升级解决的问题，即使窗口大小增长到 1M tokens，复杂任务依然会用完。因为 agent 不只是在生成代码，它还要理解代码库、跟踪自己的决策历史、处理工具输出、维护对话上下文。这些信息加起来增长得比窗口扩容快得多。

更深层的问题在于，agent 产生的信息不是均匀重要的。中间推理步骤包含决策的"为什么"，但是最终输出只包含"是什么"，即代码本身。压缩策略通常保留后者但丢了前者。下一个会话看到代码却不知道中间推理步骤的“为什么”。

那如何让跨对话的任务保持上下文连续呢？

把 agent 当成一个每次会话都会清空短期记忆的工程师来管理。 每次它要"下班"之前，必须把关键信息写下来，让下一个"接班"的 agent 能快速上手。通过状态持久化文件，让新会话能无歧义地恢复到上次离开的地方。从而降低新对话恢复到可恢复状态的重建成本，减轻会话边界切换引起的agent理解漂移。有以下工具：

- 工具1: 进度文件 (PROGRESS.md).

```Markdown
# 项目进度

## 当前状态
- 最新 commit: abc1234 (feat: add user preferences endpoint)
- 测试状态: 42/43 通过 (test_pagination_edge_case 失败)
- Lint: 通过

## 已完成
- [x] 用户模型和数据库迁移
- [x] 基础 CRUD 端点
- [x] 认证中间件集成

## 进行中
- [ ] 分页功能 (90% - 边界条件测试失败)

## 已知问题
- test_pagination_edge_case 在空结果集时返回 500
- 需要确认是否要在列表中包含已删除用户

## 下一步
1. 修复分页边界条件 bug
2. 添加"是否包含已删除用户"的查询参数
3. 更新 API 文档
```

- 工具 2：决策日志（DECISIONS.md）。记录重要的设计决策和原因。不需要详细的设计文档，只需要"什么决策、为什么、什么时候做的"：

```Python
# 设计决策

## 2024-01-15: 使用 Redis 缓存用户偏好
- 原因: 读取频率高（每次 API 调用都需要），数据量小
- 否决方案: 用 PostgreSQL 物化视图（变更频率高，物化视图维护成本不划算）
- 约束: 缓存 TTL 设为 5 分钟，写入时主动失效
```

- 工具 3：git 提交作为检查点。 每完成一个原子工作单元就提交，commit message 要说清楚做了什么和为什么。这是免费的、自动版本化的状态快照。

- 工具 4：init.sh 或 harness 的初始化流程。 在 `AGENTS.md` 里写明每次"上班"和"下班"的流程：

```Markdown
## 每次会话开始时（上班）
1. 读 PROGRESS.md 了解当前状态
2. 读 DECISIONS.md 了解重要决策
3. 跑 make check 确认仓库处于一致状态
4. 从 PROGRESS.md 的"下一步"部分继续工作

## 每次会话结束前（下班）
1. 更新 PROGRESS.md
2. 跑 make check 确认一致状态
3. 提交所有已完成的工作
```

- 混合策略：不需要每次都重置上下文。短任务（30 分钟以内）可以在同一个会话里完成，长任务（跨会话）必须用进度文件和决策日志来维持连续性。判断标准：如果任务需要的上下文超过窗口的 60%，就开始准备交接。

没有状态持久化文件的时候，每个新会话都要重新摸索：

![Image](assets/images/e5279e9b4e/image-07.png)

有状态持久化文件的时候，新会话能快速接上：

![Image](assets/images/e5279e9b4e/image-08.png)

Anthropic 在长运行 agent 研究中观察到一个有意思的现象：当 agent 感觉上下文快满了，它们会表现出"赶工收尾"的行为，匆忙结束当前工作，跳过验证步骤，或者选一个简单的方案而不是最优方案。Anthropic 把这叫"上下文焦虑"。

上下文焦虑的深层分析

Anthropic 在 2026 年 3 月发布的研究进一步揭示了上下文焦虑的具体表现：在 Sonnet 4.5 上，当上下文接近窗口限制时，agent 会表现出强烈的"赶工收尾"行为。

针对这个现象，有两种策略：

- 压缩（Compaction）：在同一个会话里把早期对话摘要化。优点是保留连续性，agent 能看到"是什么"，缺点是"为什么"经常在摘要中丢失。更关键的是，压缩并不能消除上下文焦虑

- 重置（Context Reset）：完全清空上下文，开一个新会话，从持久化工件重建。优点是干净的心理状态，新会话没有"我快没时间了"的焦虑。缺点是依赖交接工件的完备性，如果进度文件里漏了关键信息，新会话可能在错误方向上浪费时间。

Anthropic 的实际数据：对于 Sonnet 4.5，上下文焦虑足够严重，以至于压缩单独不够用，上下文重置成为 harness 设计的关键组件。但对于 Opus 4.5，这种行为大幅减弱，可以不依赖重置而靠压缩管理上下文。这意味着：harness 设计需要对目标模型有具体的理解，而不是套用通用模板。

### 3、让 agent 每次工作前先初始化

---

在使用agent开发项目时一个常见的低效模式是：让 agent 直接开始做功能，一上来直接让它写代码。这种开发模式对于小型任务可能还够用，但是面对大型任务就会存在着很多的风险。

最直接的问题是基础设施搭不牢。Agent 花了 80% 的精力写功能代码，剩下 20% 随便搭了点基础设施。测试框架配了但没验证过，lint 规则设了但太宽松，进度文件没创建。这些缺陷可能在第一个会话里不明显，但到一旦跨越到第二个会话就暴露了：新 agent 不知道项目怎么跑、怎么测、做到哪了。

更隐蔽的代价是"未验证的累积"。在测试框架配好之前写的功能代码，等回头补测试的时候可能发现设计上就有问题，早知道的话应该用不同的方式实现。前面写的代码越多，后面需要推翻重来的就越多。

更好的做法是，在让 agent 开始干活之前，先用一个独立的阶段把基础环境搭好、验证命令跑通、项目结构搞清楚。

Anthropic 在他们的长运行应用开发研究中明确建议把初始化和实现分离。他们的实验数据表明使用独立初始化阶段的项目，多会话场景中的功能完成率比混合方式高 31%。而且初始化阶段投入的时间在后续 3-4 个会话中就能完全收回。

把初始化当作一个独立的阶段来执行。 第一个会话只做初始化，不写任何业务功能代码。初始化的产出是：

1. 可运行的环境。 项目能启动、依赖都装好、没有环境问题。

2. 可验证的测试框架。 至少有一个示例测试能通过，证明测试框架本身是配好的。

3. 启动就绪清单文档。 一个明确的文档告诉后续会话：

```Markdown
# 初始化契约

## 启动命令
- 安装依赖：`make setup`
- 启动开发服务器：`make dev`
- 运行测试：`make test`
- 完整验证：`make check`

## 当前状态
- 所有依赖已安装并锁定
- 测试框架已配置（Vitest + React Testing Library）
- 示例测试通过（1/1）
- Lint 规则已配置（ESLint + Prettier）

## 项目结构
- src/ — 源代码
- src/components/ — React 组件
- src/api/ — API 客户端
- tests/ — 测试文件
```

4. 任务分解。 把整个项目拆成有序的任务列表，每个任务有明确的验收标准：

```Markdown
# 任务分解

## Task 1: 用户认证基础
- 实现 JWT 认证中间件
- 添加登录/注册端点
- 验收标准：pytest tests/test_auth.py 全部通过

## Task 2: 用户资料页面
- 实现用户资料 CRUD
- 添加资料编辑表单
- 验收标准：pytest tests/test_profile.py 全部通过

## Task 3: 搜索功能
- ...
```

5. Git 提交作为检查点。 初始化完成后提交一个干净的 checkpoint。后续所有工作都从这个 checkpoint 开始。

初始化的完成条件：启动就绪清单的四个条件全部满足——能启动、能测试、能看进度、能接手下一步。用这个检查清单验收初始化：

```Markdown
## 初始化验收清单
- [ ] `make setup` 从零开始能成功
- [ ] `make test` 至少有一个测试通过
- [ ] 新的 agent 会话能只看仓库回答"怎么跑"和"怎么测"
- [ ] 任务分解文件存在且有至少 3 个任务
- [ ] 所有内容已提交到 git
```

### 4、给agent划清每次任务的边界

---

Anthropic 在 "Effective harnesses for long-running agents" 工程博客中明确指出：当提示太宽泛时，agent 倾向于"同时启动多件事"而非"先做完一件事"。OpenAI 在 Codex 工程实践中也发现，没有显式范围控制的任务，完成率会暴跌。这本质上是一个 harness 设计问题：没有给 agent 划清边界。

Agent 天生就有"多做一点"的冲动：看到相关的事情就顺手一起做了，这存在越界行为。问题是，同时做太多事情，结果往往每一件都做不好。这是为什么呢？

这本质上是一个数学问题。假设 agent 的上下文容量为 C，同时激活 k 个任务，每个任务平均获得 C/k 的推理资源。当 C/k 低于完成单个任务所需的最小阈值时，所有任务都做不完。

agent的注意力资源是有限的，很容易出现下面两个问题：

- 过度延伸（Overreach）：agent 在一次会话中激活的任务数量超过最优值。这是可以量化的：同时做 5 个功能但 0 个跑通，就是 overreach。

- 不足完成（Under-finish）：已启动的任务中，通过端到端验证的比例低于阈值。写了代码但没跑通测试，就是 under-finish。

这两个问题互相加剧。overreach 导致注意力分散，注意力分散导致 under-finish，under-finish 留下的半成品代码又增加了系统复杂度，进一步导致下一个任务的 overreach，形成恶性循环。

用 Kanban 的话说：Little 定理告诉我们 L = lambda * W。如果在正在被服务的L 过大（同时做太多事），每个任务的等待时间 W 必然增加。对 agent 来说，这意味着每个功能从开始到验证通过的时间被拉长，失败概率被放大。

有下面四个解决思路：

- 强制 WIP=1

这是最直接有效的方法。在harness 里，明确告诉 agent：任何时刻只允许一个任务处于"进行中"状态。 在 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md 里写：

```Plain Text
## Work Rules
- Work on one feature at a time
- Only start the next feature after the current one passes end-to-end verification
- Don't "also refactor" feature B while implementing feature A
```

- 给每个任务定义显式的完成证据

完成指的是"行为验证通过了"。在你的功能列表里，每个条目都要有验证命令：

```Plain Text
F01: User Registration
  Verification: curl -X POST /api/register -d '{"email":"test@example.com","password":"123456"}' | jq .status == 201
  State: passing
```

- 把范围表面外部化

用一个机器可读的文件（JSON 或 Markdown）记录所有任务的状态。任何新会话都能直接读这个文件，知道：哪个任务在做？什么行为算完成？已经通过了什么验证？

- 监控验证完成率

harness 应该持续跟踪 VCR（Verified Completion Rate）= 已通过验证的任务数 / 已启动的任务数。VCR \< 1.0 时，阻止新任务启动。

## 四、The Future of Harnesses

---

### 1、The Coupling of Model Training and Harness Design

---

看看几个你熟悉的工具：

- Claude Code 的设计就体现了 harness 思想。它会读你仓库里的 `CLAUDE.md`，能用 shell 跑命令，在你的本地环境里执行，有会话历史，能跑测试看结果。但如果你不告诉它怎么跑测试，它就没法验证自己做得对不对。

- Cursor 也是类似的逻辑。`.cursorrules` 文件是它的指令来源，终端是它的工具，它能读你的项目结构和 lint 配置。不过 Cursor 的状态管理相对弱，你关掉 IDE 再打开，上次的上下文就没了。

- Codex（OpenAI 的 coding agent）用 git worktree 隔离每个任务的运行环境，配合本地的可观测性栈（日志、指标、追踪），让每个变更都在独立的环境中验证。它在有 `AGENTS.md` 和清晰验证命令的仓库里，表现远超在"裸"仓库里。

- AutoGPT 则是反面教材。缺乏结构化的状态管理导致长任务中上下文不断累积，缺乏精确的反馈机制导致 agent 陷入循环。很多人说 AutoGPT "不行"，但其实是它的 harness 不行。

如今诸如 Claude Code、Codex 这类智能代理产品，是把模型和harness一同纳入训练闭环来做后训练的。这有助于模型在那些被harness设计者认为应该擅长的任务上表现得更加出色，比如文件系统操作、Bash 脚本执行、计划制定，以及利用子代理进行并行处理等工作。

这就形成了一套反馈闭环：先挖掘出实用的primitives，将其集成到harness中，随后用于下一代模型的训练。随着该循环不断往复，模型在这套它所适配训练的harness内，能力会变得越来越强。

![Image](assets/images/e5279e9b4e/image-09.png)


但这种共同进化对泛化能力产生了一些有趣的影响。例如，工具逻辑的变化会导致模型性能下降。

### 2、Harnesses don’t shrink, they move

---

![Image](assets/images/e5279e9b4e/image-10.png)



上一节中的几乎所有概念都体现在这个图表中。上下文注入属于知识层的功能。循环状态保存在内存存储和工作树隔离器中。破坏性操作钩子位于权限门之后。子代理上下文防火墙则构成了整个多代理层。工具调度注册表则是 MCP 服务器和 bash 接口所在的区域。

![Image](assets/images/e5279e9b4e/image-11.png)

随着模型能力不断增强，如今托管在harness中的一部分功能，将会被内化吸纳到模型自身之中。模型将能够更擅长规划、自我验证以及保持长期的一致性，因此就不需要过多的context injection了。

这表明，随着时间的推移，harness的重要性会逐渐降低。不过，正如prompt engineering至今仍然具有价值一样，harness engineering在未来也仍有可能宝刀未老。

### 3、Harness-as-a-Service

---

Viv（Vivek Trivedy）另一项观点输出，就是在他博客提出的 HaaS（Harness‑as‑a‑Service，运行框架即服务） 这套概念框架。他的核心洞察是：开发者正在从基于大模型 LLM API做开发（这类 API 只返回文本补全结果），转向基于Harness API做开发。 Claude Agent SDK、Codex SDK、OpenAI Agents SDK，全部都印证了这个发展趋势。开发者开箱即可拿到任务循环、工具能力、上下文管理、生命周期钩子、沙箱底层原语，只需要在此基础上做定制改造。

这种变革非常重要，因为过去默认的做法是：自己构建循环、自己设计工具调用机制、自己管理对话状态、自己设计审批流程。而现在，默认的做法是：选择一个框架结构，根据系统提示、工具、上下文以及子代理这四个要素对其进行配置，然后将精力集中在针对特定领域的提示和工具设计上。
