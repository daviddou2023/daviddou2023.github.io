## 一. python大模型API限流处理

在调用LLM API时候，服务提供方会设置请求频率限制，以防止资源滥用。若未妥善处理限流策略，可能导致请求被拒绝或者IP被临时封禁。



### 1.1 重试与退避策略

可以采用指数退避算法结合随机抖动进行重试。展示了tenacity库实现自动重试示例：

```Python
# 从tenacity库中导入重试装饰器 @retry,以及停止策略和等待策略
from tenacity import retry, stop_after_attempt, wait_exponential
import requests
import time

# 定义重试装饰器，应用于下方的call_llm_api函数
# stop=stop_after_attempt(5): 最多试五次
# wait=wait_exponential(): 每次重试之间指数退避，基础等待1s,最大不超过10s
@retry(stop=stop_after_attempt(5), wait=wait_exponential(multiplier=1, max=10))
def call_llm_api(prompt):
    """
    调用LLM API 的封装函数，带有自动重试机制
    
    参数：
        prompt(str)：发送给LLM的请求内容
        
    返回：
        dict：API 响应体的 JSON 数据
        
    异常数据：
        当 API 返回HTTP 429状态码时，说明请求频率过高触发了限流，函数会主动抛出异常，
        由 @retry 装饰器捕获并且触发自动重试。
    
    """
    
    response = requests.post(
        "https://api.example.com/v1/completions",
        json={"prompt": prompt},
        headers={"Authorization": "Bearer YOUR_TOKEN"}
    )
    
    if response.status_code == 429:
        # 该异常会被 @retry 装饰器捕获，从而触发自动重试机制
        raise Exception("请求过于频繁，触发限流")
    return response.json
```

以上指数退避算法的逻辑就是，请求过于频繁触发限流后，触发自动重试机制，首次等待1秒，随后等待时间按照指数增长，最大间隔10s，最多尝试五次。

## 二. 限流核心算法原理和选型分析

### 2.1 令牌桶算法

令牌桶算法通过维护一个固定容量的“桶”，以恒定速率向其中添加令牌。每次请求需消耗一个令牌，桶空则拒绝请求。该机制允许突发流量在桶内有足够令牌时通过，实现平滑限流。

数学模型表达

设桶容量为 b（burst size），令牌生成速率为 r（rate per second），当前令牌数为 n，则任意时刻 t 的令牌增量为：

n(t)=min(b,n0+r⋅Δt)

此模型支持突发处理能力，同时保证长期平均速率不超过 r。 

### 2.2 漏斗算法

用于控制数据流量的速率，确保系统在高并发场景下平稳运行。其核心思想是将请求视为流入桶中的水，而桶以恒定速率“漏水”，即处理请求。  

当请求到达时，若桶未满，则请求被缓存；若已满，则请求被丢弃或拒绝。无论瞬时流量多大，输出速率始终保持恒定，从而实现平滑流量的目的。

### 2.3 两种算法在高并发调用下的行为对比

在高并发场景下，有两种同步思路：传统锁机制和无锁CAS算法。他们都能保证共享数据的一致性，但是实现方式和性能特征很不一样。

- 传统锁机制比如mutex ，reentrantlock本质上悲观锁：假设多个线程会同时修改共享资源（悲观考虑最差情况），所以每次访问前都要先加锁。

锁机制的特点：

（1）互斥访问：同一个时刻只有一个线程能进入临界区

（2）线程阻塞：没抢到锁的线程会被挂起，进入等待状态

（3）上下文切换开销：线程阻塞和唤醒需要操作系统参与，涉及用户态/内核态切换

（4）适合复杂操作：如果一段逻辑要修改多个共享变量，访问多个资源，锁更容易保证整体一致性。

锁的问题就是：当竞争激烈时，大量线程排队等待锁，会导致阻塞，唤醒和上下文切换，影响吞吐量。



- 无锁算法通常基于CAS（compare-and-swap），相对而言是一种乐观锁：先假设没有冲突，直接尝试更新，如果冲突了就重试。

CAS操作有三个关键参数：

（1）内存位置 V：要修改的共享变量地址

（2）预期旧值 A：线程读取到的旧值

（3）新值 B：希望写入的新值

CAS的原子性不是靠软件锁实现的，而是靠CPU硬件指令。因为CAS不会让线程进入阻塞状态，失败时只是“重试”，所以它属于非阻塞同步。在竞争不激烈时，线程不会被挂起，没有锁获取/释放的开销，没有线程阻塞唤醒带来的上下文切换，因此吞吐量通常更高。

但是在极高的竞争场景下，CAS也可能变差：多个线程频繁失败，会不断自旋重试，自旋会占用CPU，缓存行会频繁失效，增加内存总线压力。

##### 响应延迟分布

但是也不能盲目崇拜CAS，CAS也面临着ABA问题（值从 A 变成 B，又变回 A，CAS 会误以为没有变化）以及自旋开销。

### 2.4 LLM API调用场景下的限流需求建模

在大模型API调用中，高并发请求易导致服务过载，需建立精准的限流模型保障系统稳定性。  

##### 限流策略分类

- **固定窗口计数器**：简单高效，但存在临界突刺问题

- **滑动窗口**：更平滑地统计请求，适合突发流量控制

- **令牌桶**：支持突发流量，灵活性高

- **漏桶算法**：强制匀速处理，适用于严格速率限制



## 三. 基于python的限流核心算法实现

### 3.1 使用threading与queue实现令牌桶

令牌桶算法通过控制请求的处理速率，有效防止资源过载。

令牌桶以固定速率向桶内添加令牌，每次请求需先获取令牌才能执行。若桶满则丢弃多余令牌，若无可用令牌则阻塞或拒绝请求。

使用python的 threading.Lock 和 queue.Queue 可构建线程安全的令牌桶：

```Python
import time
import threading
from queue import Queue

class TokenBucket:
    """
    令牌桶限流器：
    
    核心思想：
        1. 维护一个容量为 capacity 的桶，桶中存放令牌
        2. 令牌以固定速率 fill_rate 持续注入桶中，注满即溢出
        3. 每次请求/任务需要消耗 tokens 个令牌；桶内令牌足够则放行并扣除，不足以拒绝
    
    与漏斗的区别：令牌桶允许短时突发burst,只要桶内有积攒的令牌就可以一次性消耗完，
    适合“平均速率受限，但允许瞬间突发”的限流场所。
    
    本实现通过 threading.Lock 保护临界区，适合多线程共享同一个限流器实例
    """
    
    def __init__(self, capacity, fill_rate):
        """
        初始化令牌桶
        
        capacity: 桶的最大容量
        fill_rate: 令牌的填充速率
        """
        self.capacity = capacity
        self.fill_rate = fill_rate
        self.tokens = capacity # 当前桶内令牌数，初始设置为桶满
        self.last_time = time.time()
        self.lock = threading.Lock() # 互斥锁：保证多线程并发调用 consume 时状态一致
        
    def consume(self, tokens=1):
        """
        尝试从桶中消费指定数量的令牌
        
        执行流程：
            1. 加锁进入临界区（保证线程安全）
            2. 计算自从上次调用以来流逝的时间 elapsed
            3. 按照 elapsed * fill_rate 补充令牌，并用 min 封顶防止超过 capacity
            4. 更新时间戳 last_time = now, 无论是否消费成功都要更新
            5. 判断余额是否足够：够则扣减并返回 True, 不够则保留余额并返回Fasle       
        """
        with self.lock:
            now = time.time() # 取当前时间戳
            elapsed = now - self.last_time
            # 补充令牌
            self.tokens = min(self.capacity, self.tokens + elapsed * self.fill_rate)
            self.last_time = now
            
            if self.tokens >= tokens:
                self.tokens -= tokens
                return True
            return False       
```

上述实现中 consume 方法在加锁之后计算自从上次调用以来生成的令牌数，并更新当前的令牌量。只有当前令牌充足才允许请求通过。



### 3.2 利用asyncio构建异步漏桶控制器

漏桶以恒定速率“漏水”（处理请求），新请求则持续“进水”。当进水速率超过漏水速率，多余请求将被拒绝或排队。

```Python
import asyncio
import time

class LeakyBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate # 漏水速率
        self.capacity = capacity # 漏桶容量
        self.water = 0 # 当前水量
        self.last_time = time.time()
        
    async def allow(self) -> bool:
        now = time.time()
        leak_amount = (now - self.last_time) * self.rate # 这段时间内漏掉的水量
        self.water = max(0, self.water) # 漏水，且不低于0
        self.last_time = now
        
        if self.water < self.capacity:
            self.water += 1 # 注水一滴
            return True
        return False 
        
```

上述代码通过asyncio实现非阻塞检查，每次调用 allow() 时动态计算漏水量，并更新当前的负载状态。



### 3.3 高性能限流器设计：装饰器 与上下文管理器封装

通过将限流逻辑封装为装饰器和上下文管理器，既能提升代码可读性，又能实现资源的统一管控。



```Python
import time
# 把限流器包装成**装饰器**，同时保留被装饰函数的元信息（__name__、__doc__、参数签名等）
from functools import wraps
 
class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity  # 桶容量
        self.refill_rate = refill_rate  # 每秒补充令牌数
        self.tokens = capacity
        self.last_refill = time.time()
 
    def _refill(self):
        now = time.time()
        delta = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + delta * self.refill_rate)
        self.last_refill = now
 
    def acquire(self):
        self._refill()
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False
```

### 4.1 Hugging Face  Inference API的漏桶限流实践

```Python
import time
from collections import deque
 
class LeakyBucket:
    def __init__(self, capacity: int, leak_rate: float):
        self.capacity = capacity  # 桶容量
        self.leak_rate = leak_rate  # 每秒漏水速率
        self.water = 0  # 当前水量
        self.last_leak = time.time()
 
    def allow_request(self) -> bool:
        now = time.time()
        leaked_water = (now - self.last_leak) * self.leak_rate
        self.water = max(0, self.water - leaked_water)
        self.last_leak = now
 
        if self.water + 1 <= self.capacity:
            self.water += 1
            return True
        return False
```

### 4.2 分布式环境下Redis+Lua实现跨进程限流

```SQL
local key = KEYS[1]
local limit = tonumber(ARGV[1])

end
```

该脚本通过 `INCR` 增加访问计数，首次设置过期时间，确保滑动窗口内统计准确。返回值为 1 表示允许请求，0 表示被限流。
