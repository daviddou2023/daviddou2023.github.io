### 2.1 总览与定位

SQLAlchemy是 python生态中最流行的 ORM，其设计非常优雅，分为底层的core（底层连接池+SQL）和上层的传统ORM（对象映射）两层。SQLAlchemy是后端与关系型数据库之间的数据访问层：它接收业务代码的查询和写入操作，通过数据库驱动和数据库交互。

![Image](assets/images/a8c7998ebf/image-01.png)

Python 乃至其他语言的大多数 ORM 中，都没有实现很好的分层设计， 比如 django 的 ORM，数据库链接和 ORM 本身完全混在一起。

下面来看一下SQLAlchemy的工作流程：

> 例如用户调用 `POST /tasks` 提交 BV 号后，FastAPI 接口把数据交给业务逻辑；业务逻辑创建一个 `Task` 对象，并通过 SQLAlchemy 的 `Session` 保存它。SQLAlchemy 根据 `Task` 模型生成 `INSERT` 语句，通过数据库驱动发给 SQLite 或 MySQL，提交成功后，任务记录便保存在数据库中。之后用户调用 `GET /tasks/{task_id}`，业务逻辑用 SQLAlchemy 查询该任务；SQLAlchemy执行相应的 `SELECT`，再把查到的数据转换成 `Task` 对象，供接口读取状态并返回给用户。
>

#### 为什么要有 Core

Core 层主要实现了客户端连接池。作为现代 Web应用的核心，关系型数据库的并发连接能力往往不是很强，这是因为连接有资源成本，而连接上的操作还必须共享并协调同一批数据，不是说关系型数据库不能处理大量请求，而是说不适合让大量请求各自长期占有一个数据库连接。连接池可以让应用复用有限的连接，请求只在执行数据库操作时借用，用完归还。

连接池大体分为两种，一种在服务端，也就是作为一个专门的连接池中间件，给短连接每次分配一个长连接复用；另一种在客户端，一般作为第三方库引入代码中。

SQLAlchemy的连接池显然是客户端的，在这个连接池中，SQLAlchemy维护了一定数量的长连接，当调用 `connect`时，实际上是从池子中取出了一个链接，调用 `close `时，实际是放回到了池子中的一个链接。

### 2.2 Core层：直接使用SQL

#### 2.2.1 创建连接池

SQLAlchemy中使用 `create_engine `来创建连接池。create_engine() 创建的是管理数据访问的Engine 对象。Engine持有数据库配置和连接池，代码真正执行SQL时，才会从连接池取得连接。

##### 2.2.1.1：创建 MySQL Engine

```Python
from sqlalchemy import create_engine

engine = create_engine(
    "mysql://user:password@localhost:3306/dbname",
    echo=True,  # echo 设为 True 会打印出实际执行的 sql，调试的时候更方便
    future=True, # SQLAlchemy 2.0 默认，可省略参数
    pool_size=5, # 连接池的大小默认为 5 个，连接按需建立，使用后放回池中复用
    pool_recycle=3600, # 连接存活超过 3600 s后，SQLAlchemy会在下次借出这个连接时回收并重建它。
)

```

连接地址可以拆分为如下：

```Python
mysql://user:password@localhost:3306/dbname
  │       │     │          │       │     └─ 数据库名
  │       │     │          │       └─────── 端口
  │       │     │          └─────────────── 数据库主机
  │       │     └────────────────────────── 密码
  │       └──────────────────────────────── 用户名
  └──────────────────────────────────────── 数据库类型
```

SQLAlchemy自己不直接实现所有数据库的网络通信，它需要调用相应的数据库驱动。在这个 MySQL URL中没有显式指定驱动，默认用 `mysqldb`，它由 `mysqlclient`包提供。因此要有相应驱动才能真正连接 MySQL。

##### 2.2.1.2：创建 SQLite 数据库

```Python
# 创建一个 SQLite 的内存数据库
engine = create_engine("sqlite:///:memory:", echo=True, future=True,
    connect_args={"check_same_thread": False})
```

- `sqlite:///:memory`：表示创建内存中的 SQLite 数据库，它适合简单实验，程序结束就消失，要实现持久化，应该使用SQLite数据库。

- `connect_args`中的参数会传给底层 SQLite驱动，`check_same_thread=False`允许一个SQLite连接在创建它的线程之外使用。

##### 2.2.1.3：显式指定 MySQL 驱动

```Python
# pip install mysqlclient
engine = create_engine('mysql+mysqldb://user:password@localhost/foo?charset=utf8mb4')
```

它和第一段都连接 MySQL，但这里显式写出了驱动名：

```Plain Text
mysql + mysqldb
数据库   数据库驱动
```

`mysqldb` 对应前面安装的 `mysqlclient` 包。URL 后面的 `charset=utf8mb4` 指定连接使用的字符集，便于正确处理中文等 Unicode 字符。

##### 2.2.1.4：Engine如何参与一次查询

业务代码要查询任务，Engine从连接池借出一个连接，数据库驱动把SQL发给 SQLite/MySQL，数据库返回查询结果，连接归还连接池，等待下次复用。

Engine负责管理数据库访问基础设施，之后使用的 `Session `或者 `AsyncSession `会基于它完成 ORM操作。



#### 2.2.2 CRUD基础

假设已经创建了同步 `engine`，数据库中也已有 `some_table` 表，包含 `id`、`x`、`y` 三列，且 `id` 是主键。

```Python
from sqlalchemy import text

# Create 插入两行，正常离开 begin 块时自动提交
with engine.begin() as conn:
    conn.execute(
        text("INSERT INTO some_table (id, x, y) VALUES (:id, :x, :y)"),
        [
            {"id": 1, "x": 11, "y": 12},
            {"id": 2, "x": 13, "y": 14},
        ],   
    )

# Read：查询并读取结果
with engine.connect() as conn:
    result = conn.execute(
        text("SELECT id, x, y FROM some_table WHERE y > :min_y"),
        {"min_y": 10},
    )
    rows = result.all()
    
    for row in rows:
        print(row.id, row.x, row.y)
        
# Update：修改 id=1 的记录，正常结束时自动提交
with engine.begin() as conn:
    conn.execute(
        text("UPDATE some_table SET y = :new_y WHERE id = :id"),
        {"new_y": 20, "id": 1},
    )
    
# Delete：删除 id=2 的记录，正常结束时自动提交
with engine.begin() as conn:
    conn.execute(
        text("DELETE FROM some_table WHERE id = :id"),
        {"id": 2},
    )

```

这里 `engine.connect()` 用于读取；三个写入操作使用 `engine.begin()` 管理事务，正常结束时提交，发生异常时回滚。`result.all()` 只调用一次，后续遍历保存结果的 `rows`。所有动态值都通过 `:参数名` 和字典传入。

#### 2.2.3 事务与 commit

SQLAlchemy 提供两种提交的方式，一种是手工 commit，一种是半自动 commit。官方文档建议使用 engine.begin()。还有一种完全自动的，每一行提交一次的 autocommit 方式，不建议使用。

```JavaScript
# "commit as you go"  需要手动写 commit
with engine.connect() as conn:
    conn.execute(text("CREATE TABLE some_table (x int, y int)"))
    conn.execute(
        text("INSERT INTO some_table (x, y) VALUES (:x, :y)"),
        [{"x": 1, "y": 1}, {"x": 2, "y": 4}]
    )
    conn.commit()  # 注意这里的 commit
    
# "begin once"  半自动 commit
with engine.begin() as conn:
    conn.execute(
        text("INSERT INTO some_table (x, y) VALUES (:x, :y)"),
        [{"x": 6, "y": 8}, {"x": 9, "y": 10}]
    )
```

### 2.3 ORM入门：Session与声明式模型

#### 2.3.1 Session 的基本使用

一个Session 对应一次数据库对话，它持有连接、管理对象状态、负责把Python对象的变化翻译成SQL，并在commit时候统一提交。

它有几个关键特点：

- Session 不是线程安全的：一个session实例不能被多个线程同时使用

- web框架通常每个请求创建一个session：请求之间天然隔离，所以“非线程安全”在典型web场景下不是问题

- session是状态化的：它会跟踪 add 的对象，修改的属性，直到commit或者rollback

第一种写法：

```Python
from sqlalchemy.orm import Session

# 用 engine创建一个 Session实例。engine提供连接池，Session从池中取连接
with Session(engine) as session:
    session.add(foo) # 把对象 foo 加入 Session的“待持久化”集合，此时还没发SQL
    session.commit() # 这时SQLAlchemy才会把 foo 翻译成 INSERT 并发给数据库
```

这种写法适合一次性脚本或者简单场景，因为每次都要手动传engine

第二种写法：

```Python
from sqlalchemy.orm import sessionmaker
new_session = sessionmaker(engine)

with new_session() as session:
    ...
```

- `sessionmaker(engine)` 创建一个工厂函数，把engine（以及可能的其他配置）预先绑定进去。

- `new_session()`：调用工厂，得到一个 Session实例

使用 sessionmaker工厂创建Session可以避免重复传参：如果 Session需要很多配置，工厂可以统一预设；FastAPI、Flask等通常会在应用启动时创建一个 `sessionmaker`，每个请求调用一次 `new_session()` 得到独立 Session。

典型 FastAPI 依赖注入写法：

```Python
from sqlalchemy.orm import sessionmaker, Session

SessionLocal = sessionmaker(engine)

def get_db():
    db = SessionLocal() # 每次请求调用 get_db()，得到一个独立的Session
    try:
        yield db
    finally:
        db.close()
```

#### 2.3.2 声明式API与建表

```Python
from datetime import datetime, timezone

from sqlalchemy import (
    DateTime,
    Integer,
    String,
    Text,
    UniqueConstraint,
    func,
)
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"
    __table_args__ = (
        UniqueConstraint("name", "time_created"),
    )

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(30), index=True)
    fullname: Mapped[str] = mapped_column(String(100), unique=True)
    description: Mapped[str] = mapped_column(Text, deferred=True)

    time_created: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
        nullable=False,
    )
    time_updated: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
        onupdate=func.now(),
        nullable=False,
    )
# 调用 create_all 创建所有模型
Base.metadata.create_all(engine)

# 如果只需要创建一个模型
User.__table__.create(engine)
```

上段声明式 API 定义了“如何用Python类描述一张数据库表”。从宏观上看声明式模型可以分为三层：

```Python
class Base(DeclarativeBase): # 1. 基类
    pass
class User(Base):            # 2. 模型类：一个类对应一张表
    __tablename__ = "users"  # 3. 表名 + 字段
    
Base.metadata.create_all(engine) # 4. 建表
```

（1）表名与联合约束

```Python
__tablename__ = "users"
# 表级约束，每个(UniqueConstraint(...),)元素是一个 tuple
__table_args__ = (UniqueConstraint("name", "time_created"),)
```

（2）主键

```Python
id: Mapped[int] = mapped_column(Integer, primary_key=True)
```

- `Mapped[int]`：映射后id 变量的类型是 int

- `mapped_column`：SQLAlchemy ORM 提供的**函数，**创建列的映射配置。`Integer` 表示数据库列使用整数类型；`primary_key=True` 表示它是主键。

（3）普通字段 + 索引

```Python
# index=True 为 name 建立普通索引
name: Mapped[str] = mapped_column(String(30), index=True)
# unique=True 为 fullname 建立唯一索引
fullname: Mapped[str] = mapped_comuln(String, unique=True)
```

（4）延迟加载大字段

```Python
# deferred=True，默认查询不加载这个字段
description: Mapped[str] = mapped_column(Text, deferred=True)
```

（5）默认值

```Python
# default=datetime.now 生效位置在 Python端
time_created: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=datetime.now)
# server_default=func.now() 生效位置在数据库端
time_created: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
time_updated: Mapped[datetime] = mapped_column(DateTime(timezone=True), onupdate=func.now())
```

（6）建表的两种方式

```Python
Base.metadata.create_all(engine) # 创建所有模型对应的表
User.__table__.create(engine) # 只创建 User 这一张表
```

- `Base.metadata` 收集了所有继承 `Base `的模型，`create_all `批量建表

- `User.__table__` 是模型对应的 Table 对象，`.create(engine)`只建这一张表

### 2.4 ORM 关系映射

#### 2.4.1 一对多双向映射

```Python
from sqlalchemy import ForeignKey
from sqlalchemy import relationship

# 1. 声明基类
class Base(DeclarativeBase):
    pass


# 2. “一”的一方：Group
class Group(Base):
    __tablename__ = "groups"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(50), nullable=False)

    # 一 → 多：通过字符串模型名引用 User（此时 User 尚未定义）
    # back_populates 与 members.group 配对
    members: Mapped[list["User"]] = relationship(
        "User",
        back_populates="group",
    )

    def __repr__(self) -> str:
        return f"Group(id={self.id!r}, name={self.name!r})"


# 3. “多”的一方：User
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(50), nullable=False)

    # 数据库层：真实存在的外键列，位于“多”侧
    group_id: Mapped[int | None] = mapped_column(
        Integer, ForeignKey("groups.id"), nullable=True
    )

    # 多 → 一：对象导航，back_populates 与 Group.members 配对
    group: Mapped["Group | None"] = relationship(
        "Group",
        back_populates="members",
    )

    def __repr__(self) -> str:
        return f"User(id={self.id!r}, name={self.name!r}, group_id={self.group_id!r})"


# 4. 建表
engine = create_engine("sqlite:///:memory:", echo=True, future=True)
Base.metadata.create_all(engine)

```

一对多双向映射让一方通过 relationship 拿到多个多方对象列表，多方通过relationship 拿到所属的一方对象，两侧共享同一个数据库外键。

#### 2.4.2 多对多映射

多对多映射的作用是让一个用户拥有多个权限，同时让同一个权限分配给多个用户，并通过关联表保存每一组“用户-权限”关系

```Python
from sqlalchemy import Column, ForeignKey, Integer, String, Table
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship


class Base(DeclarativeBase):
    pass


# 关联表：每一行表示“某用户拥有某权限”
# 这里是普通独立的 Table，所以用 Column，不用 mapped_column
user_permissions = Table(
    "user_permissions",
    Base.metadata,
    Column("user_id", ForeignKey("users.id"), primary_key=True),
    Column("permission_id", ForeignKey("permissions.id"), primary_key=True),
)


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(50), nullable=False)
    # 一个 User 对象可以通过 permissions 属性访问其关联的 Permission 对象
    permissions: Mapped[list["Permission"]] = relationship(
        secondary=user_permissions, # 告诉 ORM 两张表之间要经过 user_permissions 关联表
        back_populates="users",
    )


class Permission(Base):
    __tablename__ = "permissions"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(50), nullable=False)
    # 通过一个权限查看拥有哪些该权限的用户
    users: Mapped[list[User]] = relationship(
        secondary=user_permissions,
        back_populates="permissions",
    )
```

#### 2.4.3 关系写入

虽然由 SQLAlchemy 管理，但你在 Python 中仍按集合属性来操作。建立关系时，操作的是 Python 对象的关系属性：

```Python
user1 = User(name="user1")
user2 = User(name="user2")
open_file = Permission(name="open_file")
save_file = Permission(name="save_file")

user1.permissions.extend([open_file, save_file]) # extend 接收可迭代对象
user2.permissions.append(open_file) # append 接受一个对象

db.add_all([user1, user2, open_file, save_file])
db.commit()
```


#### 2.5.2 更新

- 用 update 语句批量更新

```SQL
stmt = update(User).where(User.name == "john").values(name="John") \
    .execution_options(synchronize_session="fetch")
session.execute(stmt)
```

- 直接属性赋值

```Python
user.name = "John"
session.commit()
```

先 `get` 到对象，改属性，`commit` 时 SQLAlchemy 自动生成 `UPDATE`。

- 竞态条件陷阱

```Python
# 错误
user.visit_count += 1
# 正确
user.visit_count = User.visit_count + 1
```

在多并发的场景下， `user.visit_count` 是**当前这个 Python 对象里已经读到的数值**。如果它是 `1`，Python 算出 `2`，SQLAlchemy 随后大致执行：

```Python
UPDATE users SET visit_count = 2 WHERE id = ...;
```

另一个请求也可能算出 `2`。数据库无法从这条 SQL 看出“两个人各想加一次”。

而如果按照第二种写法，左侧 `user.visit_count` 是某个用户对象的属性；右侧 **`User.visit_count`**** 是模型类上的映射属性**，SQLAlchemy 会把它构造成 SQL 表达式。提交时可以生成类似：

```Python
UPDATE users
SET visit_count = visit_count + 1
WHERE id = ...;
```

两个请求分别执行这条 `UPDATE`，数据库会协调对同一行的写入。第一条把 `1` 改成 `2`，第二条再把当时的 `2` 改成 `3`。

这保证了原子性：单条语句不会被拆成应用层的先读再计算再写三个步骤。



#### 2.5.3 插入

```Python
session.add(user)
session.add_all([user1, user2, group1])
```

需要注意的是 `add/add_all` 只是把对象登记到 `Session`，此时不发 SQL，真正发SQL是在 `commit()` 或者 `flush()` 时候。

```Python
session.flush()   # 不是 commit
print(user.id)
```

`flush()`把 Session 中待持久化的改动发 SQL 给数据库，但是不提交事务。插入后数据库生成的自增id会回填到对象上，所以 flush 后能读到 user.id。flush 后事务仍然可以回滚，commit 才真正落库

#### 2.5.4 删除

```Python
session.delete(user)
```

同理只是标记为删除，commit时候才发 SQL: DELETE 语句

#### 2.5.5 整体流程与 Session 状态

一个典型的 CRUD周期：

```SQL
select/get  →  对象进入 Session（持久态）
add         →  对象进入 Session（待插入）
修改属性     →  对象标记为脏（dirty）
flush       →  发 SQL，未提交
commit      →  提交事务，对象状态与库一致
delete      →  标记删除，commit 时发 DELETE
```

假设 Task 模型已经定义，engine 也已经创建，

```Python
from sqlalchemy.orm import Session

with Session(engine) as session:
    # Create：创建 Python 对象
    task = Task(bvid="BV1xx411c7mD", status="PENDING")

    session.add(task)       # 待插入：Session 开始管理它
    session.flush()         # 发出 INSERT，但事务还没提交
    task_id = task.id       # 此时通常已经拿到数据库生成的 ID
    session.commit()        # 提交事务，任务正式持久化

    # Read：按主键取得记录
    task = session.get(Task, task_id)
    print(task.status)

    # Update：修改对象属性
    task.status = "RUNNING"  # 对象发生变化，等待更新
    session.flush()          # 发出 UPDATE，但事务还没提交
    session.commit()         # 提交更新

    # Delete：删除记录
    session.delete(task)     # 标记为待删除
    session.flush()          # 发出 DELETE，但事务还没提交
    session.commit()         # 提交删除
```



### 2.6 ORM 进阶：加载与性能

#### 2.6.1 N+1 问题与关联加载

假设你查了 N 个 User，然后对每个 User 访问 `user.groups` 去取关联数据：

```Python
users = session.execute(select(User)).scalars().all()  # 1 次查询
for u in users:
    print(u.groups)   # 每个 u 再发 1 次查询 → 共 N 次
```

总的查询数是一次主查询+每个对象的N次关联查询。数据量一大数据库往返次数爆炸。

使用 `selectinload `加载：

```Python
session.execute(
    select(User).options(selectinload(User.groups))
).scalars().all()
```

`.options(selectinload(User.groups))`：告诉 SQLAlchemy 在主查询之后，用一条额外的 `SELECT ... WHERE id IN (...)` 把关联数据一次性取回。总查询数变成 2 次（主查询 + 一条 `IN` 子查询），与 N 无关，彻底消除 N+1。

#### 2.6.2 JSON 字段的特殊处理

```Python
article = session.get(Article, 1)
tags = copy.copy(article.tags)   # 先复制
tags.append("iOS")               # 改副本
article.tags = tags              # 对 ORM 属性进行**赋值**。SQLAlchemy 能感知这次赋值，并在刷新时判断新旧值。
session.commit()
```

为什么不能直接 `article.tags.append("iOS")`？

- SQLAlchemy 判断一个字段“是否被修改”依赖属性赋值（set 操作）。

- 对 JSON 对象原地修改（append/修改 dict 键）不会触发赋值，SQLAlchemy 感知不到变化，commit 时不会生成 UPDATE，改动丢失。

- 正确做法：copy → 修改副本 → 整体赋值回属性，赋值动作让 SQLAlchemy 标记该字段为脏，才会写回。

# 三、异步数据库与会话生命周期

异步数据库负责让FastAPI 在 `await`数据库I/O 时候把执行权交还给事件循环，从而用少量线程并发处理大量请求；同时用“每个请求一个AsyncSession”

> “每个请求一个AsyncSession”是异步 web 框架中的一种使用模式：每来一个HTTP请求，就创建（或者从依赖注入中拿到）一个全新的 AsyncSession 实例，供这个请求内的所有数据库操作使用；请求结束就关闭它。
> 
> 

保证请求之间隔离、请求内事务一致，并由 Session 的 `async with`生命周期统一管理查询、commit/rollback 和连接归还，三者共同实现高并发且资源可控的数据库访问。

### 3.1 从数据库到请求的完整路径

```Python
POST /tasks
    -> FastAPI 路由
    -> Depends(get_db) 提供 AsyncSession
    -> Session 通过 Engine 取得数据库连接
    -> aiosqlite 执行 SQL
    -> 提交事务、归还连接、结束请求
```

AsyncEngine 主要保存数据库配置，管理连接池，在应用启动时创建一次

数据库连接负责与数据库通信，按需从池中借用

AsyncSession 管理一次工作中的 ORM 对象和事务，每次请求创建一个

### 3.2 创建异步 Engine 和 Session 工厂

```Python
from sqlalchemy.ext.asyncio import (
    async_sessionmaker,
    create_async_engine,
)

DATABASE_URL = "sqlite+aiosqlite:///./tasks.db"
# 创建应用共用的异步Engine
engine = create_async_engine(DATABASE_URL, echo=True)
# 创建一个“Session工厂”。之后调用 SessionLocal()，才得到某次操作使用的 AsyncSession
SessionLocal = async_sessionmaker(
    engine,
    expire_on_commit=False, # 提交后不立即让已加载的对象属性过期
)
```

### 3.3 用 yield 给每个请求提供 Session

```Python
from collections.abc import AsyncIterator
from sqlalchemy.ext.asyncio import AsyncSession
async def get_db() -> AsyncIterator[AsyncSession]: # 异步生成器依赖，产出一个 AsyncSession，路由拿到的就是它
    async with SessionLocal() as session: # 调用 SessionLocal可以得到一个新的 AsyncSession
        try:
            yield session # 暂停，路由函数开始运行
        except Exception:
            await session.rollback()
            raise
```

整个的执行顺序是：

- 请求到来，SessionLocal() 新建 AsyncSession（从池借连接）

- 执行到 yield session, 把 Session 交给路由函数

- 路由函数执行查询或者写入

- 路由结束后，依赖函数从 yield 后继续执行；async with 上下文管理器负责关闭 Session

- 如果路由向外抛出异常，执行rollback() 撤销尚未提交的事务，再用 raise 保留原异常

这里没有在 yield 后执行 `await session.commit()`。写入操作由业务代码决定何时提交，这样事务边界更清晰。

### 3.4 在路由中使用 Session

```Python
@app.post("/tasks", status_code=202) # POST /tasks接口用于提交任务，202语义是“请求已接收、任务尚未完成”
# 通过依赖注入拿到本请求专属的 AsyncSession
async def create_task(
       data: TaskCreate,
       db: Annotated[AsyncSession, Depends(get_db)] # 调用 get_db() 拿到 yield 出来的 AsyncSession
   ):
       task = Task(bvid=data.bvid, status="PENDING")
       db.add(task) # 把 task 登记到 Session的“待持久化”集合中
       
       #若 commit 前还需用 ID 做别的事（如返回、关联），flush 是必要的。
       await db.flush() # flush() 把 Session 中待持久化的改动真正发SQL 给数据库，但是不提交事务
       task_id = task.id # 执行后数据库生成的自增主键会回填到task_id
       await db.commit() # 提交事务，INSERT 真正持久化，事务结束
       
       return {"task_id": task_id, "status": "PENDING"}
       
           
```

该接口用 `Depends(get_db)` 注入每请求独立地 `AsyncSession `，把请求体校验成 `TaskCreate `后实例化 `Task `并 `add `登记；`flush `发 `INSERT `拿到自增 ID （不提交）。再显示 `commit `落库，最后返回 `202 + task_id`；异常时由 `get_db `统一 `rollback`，`commit `时机由业务掌握，事务边界清晰。

### 3.5 事务边界：多项写入要一起成功

如果创建任务时还要写入第一条 Message，希望两条记录一起成功，可以调用 `db.begin`：

```Python
async with db.begin():
    db.add(task)
    db.add(messsage)
```

正常离开 `begin()` 块时提交；块内发生异常时回滚。

### 3.6 实战习题

> 
> 

#### 3.6.1 代码实现

```Python
python -m pip install fastapi uvicorn sqlalchemy aiosqlite
```

总体的目标是：提交一个BV 号（会生成对应的ID），把任务存入 SQLite文件，之后凭ID查询；服务重启后仍能查到。程序需要回答四个问题：接收什么、保存什么、怎样取得数据库对话、怎样返回查询结果。

```Python
客户端 POST /tasks -> 校验 BV 号 -> 创建 Task -> 写入 task.db -> 返回 ID
客户端 GET /tasks/{task_id} -> 按照 ID 读 tasks.db -> 返回任务或者 404
```

##### 第一步：先定接口和数据

客户端需要发送什么数据，POST 和 GET 两个接口分别返回什么。重启后需要查到哪些信息，需要先确定数据模型。

```Python
# POST 请求体，只接收 BV 号
class TaskCreate(BaseModel):
    bvid: str = Field(pattern=r"^BV[0-9A-Za-z]{10}$")

# 任务状态的允许值
class Status(str, Enum):
    PENDING = "PENDING"
    RUNNING = "RUNNING"
    SUCCESS = "SUCCESS"
    FAILED = "FAILED"
    
# POST 成功后的响应结构：返回 task_id 和 status
class TaskAccepted(BaseModel):
    task_id: int
    status: Status

# GET 成功后的响应结构：返回 task_id 和 bvid 和 status
class GetResponse(BaseModel):
    task_id: int
    bvid: str
    status: Status
   
```

这一步只规定 HTTP 数据格式，还没有创建数据库表，也没有实现路由

##### 第二步：定义数据库要保存的数据

在服务重启后任务必须仍然存在，因此任务数据不能只放在python字典里，必须写入数据库。

需要定义Task 模型描述数据库表结构，数据库要存id、bvid、status，之后创建的 `Task(...) `对象才代表一条具体任务。

```Python
class Task(Base):
    __tablename__ = "tasks"
    id: Mapped[int] = mapped_column(primary_key=-True)
    bvid: Mapped[str] = mapped_column(String(20), nullable=False)
    status: Mapped[str] = mapped_column(String(20),nullable=False)
        
```

##### 第三步：配置 SQLite 文件库和异步 Engine

路由函数如何访问SQLite？数据库文件如何在服务重启后保留？

需要以下三个模块实现：

- SQLite 文件数据库 URL：指定 SQLite将数据存入磁盘文件（tasks.db）

- 一个模块级异步 Engine 管理数据库连接：为请求提供可复用的异步连接数据库入口，路由通过其管理的连接可以访问数据库

- 一个 Session 工厂：基于 Engine 创建 AsyncSession，让路由通过 Session使用这些连接操作数据库。

```Python
DATABASE_URL = "sqlite+aiosqlite:///./tasks.db"
engine = create_async_engine(DATABASE_URL, echo=True) # echo=True 会把 SQL 打印到终端

    engine,
    expire_on_commit=False,
)
```

##### 第四步：决定数据库表何时创建

服务启动时候，tasks 表可能还不存在，第一次请求前需要确保它已经创建。

需要用 FastAPI 的 lifespan 管理应用启动和关闭流程。启动时创建缺少的表，随后才开始接收请求。

```Python
# 为 FastAPI 定义一个生命周期钩子
@asynccontextmanager
async def lifespan(app: FastAPI):
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all) # 根据所有继承 Base 的模型生成 CREATE TABLE 并执行
    yield
```

创建 app 时后把 lifespan 接进去


##### 第五步：设计请求级数据库会话依赖

POST 和 GET 都要访问数据库，如何让路由拿到 Session，并确保请求结束后 Session 关闭、异常时事务回滚。

路由通过 `Depends(get_db)` 获取 Session，由 `get_db()` 创建 Session 并通过 yield 交给路由：

```Python
async def get_db():
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback() # 回滚撤销当亲尚未提交的任务
            raise
```

##### 第六步：实现 POST 创建路径

收到合法 BV 号后，如何生成数据库任务、取得数据库生成的id，并且确保任务已经持久化？

```Python
@app.post(
    "/tasks",
    status_code=202,
    response_model=TaskAccepted,
)
async def create_task(
    data: TaskCreate,
    db: Annotated[AsyncSession, Depends(get_db)],
):
    # 创建 ORM 对象
    task = Task(
        bvid=data.bvid,
        status=Status.PENDING.value,  
    )
    # 把对象纳入 Session 管理
    db.add(task)
    # 执行 INSERT, 把对象变成数据库里的一行
    await db.flush()
    task_id = task.id
    # 提交事务、落库任务才正式持久化
    await db.commit()
    
    return {
        "task_id": task_id,
        "status": Status.PENDING
    }
```

##### 第七步：实现 GET 查询路径

客户端拿到ID 后，如何从数据库查回任务？如果 ID 不存在，接口应该如何响应？

GET 路由要接收整数 task_id，通过依赖获得 Session，按照主键查找任务，找不到返回 404，找到时转成 GetResponse

```Python
@app.get("/tasks/{task_id}", response_model=GetResponse)
async def get_task(
    task_id: int,
    db: Annotated[AsyncSession, Depends(get_db)],
):
    # db.get(...)：Session 提供的按主键取对象的快捷方法
    task = await db.get(Task, task_id) # 按主键查询单个 ORM 对象
    
    if task is None:
        raise HTTPException(
            status_code=404,
            detail="Task not found",
        )
    return GetResponse(
        task_id=task.id,
        bvid=task.bvid,
        status=task.status,  
    )
```

# 四、任务状态与持久化设计

任务状态与持久化设计负责把任务当前进展和处理结果可靠地保存在数据库中，使接口、后台处理和服务重启都能围绕同一条任务记录工作。

### 4.1 内存状态与持久化状态

如果把任务存在 python字典中，数据只在当前 python 进程内存中。进程停止后，字典消失。而SQLite数据库则把任务写入磁盘文件，进程重启后仍可查询。

在写入数据库之前，应该先明确任务表要保存哪些信息。一个最小任务记录通常包括：

id、bvid、status、result（处理成功后的结果）、error（处理失败收的错误摘要）、created_at、updated_at（机理创建和最近更新时间）

可以对之前 创建的` Task` 模型（ORM对象）进行扩展

```Python
from datatime import datetime
from sqlalchemy import DataTime, String, Text, func
from sqlalchemy.orm import Mapped, mapped_column

class Task(Base):
    __tablename__ = "tasks"
    id: Mapped[int] = mapped_column(primary_key=True)
    bvid: Mapped[str] = mapped_column(String(20), nullable=False)
    status: Mapped[str] = mapped_column(String(20), nullable=False)
    
    result: Mapped[str | None] = mapped_column(Text, nullable=True)
    error: Mapped[str | None] = mapped_column(Text, nullable=True) # nullalbe=True 代表字段是否允许为空
    
    created_at: Mapped[datetime] = mapped_column(
        Datatime,
        server_default=func.now(), # SQLAlchemy 的 SQL 函数表达式，最终翻译成数据库的 NOW() / CURRENT_TIMESTAMP
        nullable=False
    )
    updated_at: Mapped[datetime] = mapped_column(
        Datatime,
        server_default=func.now(),
        onupdate=func.now(),
        nullable=False
    )
```

### 4.2 状态流转：明确哪些变化是合法的

任务状态的变化要符合业务流程：

```Python
PENDING → RUNNING → SUCCESS
                   ↘ FAILED
```

集中定义状态的好处是，创建、更新和响应模型使用同一套值，减少 `"pending"`、`"PENDING"` 这类不一致问题。

```C++
from enum import Enum


class TaskStatus(str, Enum):
    PENDING = "PENDING"
    RUNNING = "RUNNING"
    SUCCESS = "SUCCESS"
    FAILED = "FAILED"
```

### 4.3 一个状态变化就是一次数据库事务

状态由 PENDING 更新为 RUNNING 需要执行一次数据库事务

```Python
async def mark_task_runnning(
    session: AsyncSession,
    task_id: int
    ) -> None:
    
    task = await session.get(Task, task_id) # Task 是要查询的 ORM 模型类
    
    if task is None:
        return
    task.status = Status.RUNNING.value
    task.error = None
    await session.commit() # 提交后其他请求和新进程才能看到更新
```

状态 SUCCESS 成功时候保存结果和最终状态：

```Python
async def mark_task_success(
    session: AsyncSession,
    task_id: int,
    result_text: str,
) -> None:
    task = await session.get(Task, task_id)
    
    if task is None:
        return
        
    task.status = Status.SUCCESS.value
    task_result = result_text
    task.error = None
    await session.commit()
```

状态 FAILED 失败时要保存错误摘要

```Python
async def mark_task_failed(
    session: AsyncSession,
    task_id: int,
    error_message: str,
) -> None:
    task = await session.get(Task, task_id)
    
    if task is None:
        return
    task.status = Status.FAILED.value
    task.error = error_message
    await session.commit()
```

### 4.4 后台处理应有自己的 Session

后台处理不要复用HTTP 请求的 Session，要自己创建 Session，用完即关。

```Python
async def process_task(task_id: int) -> None:
    async with SessionLocal() as session:
        await mark_task_running(session, task_id)
    
    try:
        result_text = await run_agent(task_id)
        
        async with SessionLocal() as session:
            await mark_task_success(session, task_id, result_text)
    except Exception as exc:
        async with SessionLocal() as session:
            await mark_task_failed(session, task_id, str(exc))
```

### 4.5 `Task `当前状态和 `Message `过程记录的区别

Task.status 表示任务此刻的状态， Message 可以记录处理过程中产生的多条信息，保存过程事件、日志或者对话内容。

如果每次状态变化都覆盖 `Task.status`，你只能看到最新状态；如果同时插入一条 Message，还能回顾状态如何变化。

# 五、关系预加载与N+1查询

关系预加载和N+1查询可以帮助后端在读取ORM对象及其关联数据时控制SQL查询次数，避免查询量随记录数增长而失控。

### 5.1 区分外键和 ORM 关系

数据库通过外键保存关联，一个 Task 对应多个 Message，每个 Message 属于一个 Task。

```Python
class Task(Base):
    __tablename__ = "tasks"
    # 返回该任务下所有的 Messages 对象列表
    messages: Mapped[list["Messages"]] = relationship(
        back_populates="tasks", # 说明Task.messages 和 Message.task 是同一条外键关系的两端
        lazy="raise", # 强制显示预加载，避免 N+1 和异步下的隐式 I/O 问题
    )
    
class Message(Base):
    __tablename__ = "messages"
    # 返回该 Message 所述的 Task对象
    task: Mapped["Tasks"] = relationship(
        back_populates="messages",
        lazy="raise",
    )
```

### 5.2 懒加载

懒加载指的是先查父对象，等代码访问关联属性时，再额外查询关联数据

```Python
# 会抛错（未预加载）
task = await session.get(Task, 1)
print(task.messages)   # ❌ lazy="raise" 抛异常

# 正确：显式预加载
stmt = select(Task).options(selectinload(Task.messages)).where(Task.id == 1)
task = (await session.execute(stmt)).scalar_one()
print(task.messages)   # ✅ 已加载，正常
```

同步 ORM 中，这种额外查询可能在属性访问时悄悄发生。异步 ORM 中则需要特别小心：普通属性访问无法直接 `await`，未预加载就访问关系可能引发错误。因此异步项目通常会明确指定加载策略，并在查询时安排好所需数据。

### 5.3 N+1 查询

假设要查询100个任务，并读取每个任务的消息。如果ORM 先查一次任务列表，再为每个任务分别查消息，查询次数就是 101 次，也就是 N+1：

- 1次指的是查询父记录列表

- N次指的是每个父记录各执行一次关联查询

### 5.4 selectinload() ：常见的一对多预加载

列表接口通常会查询多个 Task，并展示每个 Task 的消息数量或者内容，可以使用 `selectinload()` 显式预加载：

```Python
from sqlalchemy import select
from sqlalchemy.orm import selectinload

statement = (
    select(Task) # 第一次查询
    .options(selectinload(Task.messages)) # 第二次查询
)

result = await session.execute(statement) # 拿到 Task 列表时，两次查询都已完成，messages 已填充
tasks = result.scalars().all()

for task in tasks:
    print(task.id, [message.content for message in task.messages])
```

大致会执行两次查询：

```Plain Text
SELECT * FROM tasks;
SELECT * FROM messages WHERE task_id IN (...);
```



### 5.5 `joinedload()`：通过 JOIN 一起查询

```Python
from sqlalchemy.orm import joinedload


statement = (
    select(Task)
    .options(joinedload(Task.messages))
)

result = await session.execute(statement)
tasks = result.unique().scalars().all()
```

joinload() 会通过 JOIN 把任务和消息放到同一条查询中。因为一个 Task 可能对应多跳 Message，SQL结果里同一个 Task 的列还会重复出现，所以要用 `result.unique()`，让 ORM 对重复的父对象去重

### 5.6 在 FastAPI 路由中使用预加载

如果需要返回任务及其消息，可以在路由查询处预加载，再组装响应：

```Python
@app.get("/tasks/{task_id}")
async def get_task(
    task_id: int,
    db: Annotated[AsyncSession, Depends(get_db)],
):
    statement = (
        select(Task)
        .options(selectinload(Task.messages))
        .where(Task.id==task_id)
    )
    
    result = await db.execute(statement)
    task = result.scalar_one_or_none()
    
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")

    return {
        "task_id": task.id,
        "messages": [message.content for message in task.messages],
    }
```



# 六、索引基础

索引是数据库为特定列维护的查找结构，让后端按照任务 ID、用户或者状态查询时更快定位记录，但是会增加存储和写入成本

### 6.1 为什么需要索引

假设 tasks 表有 100万条任务，你要查询某个任务：

```Python
SELECT id, bvid, status
FROM tasks
WHERE id = 12345;
```

如果没有可用索引，数据库可能需要逐行检查，这叫全表扫描，而如果有合适的索引，数据库可以先在索引中定位，但是索引本身也会占空间。

### 6.2 B+ 树为什么适合数据库查询

MySQL InnoDB等关系型数据库广泛使用B+ 树作为索引结构，它把键值按照顺序组织在多层节点中，查询时候不必从头逐行寻找，而是逐层缩小范围；相邻键值也适合范围查找和排序。

目前使用 SQLite，它的索引也采用 B 树类结构，但内部实现不能直接当成 MySQL InnoDB 的 B+ 树来讲。学习 B+ 树原理有助于理解 MySQL 索引。

### 6.3 索引也有成本

每插入一条任务，数据库除了保存任务记录，还可能需要更新相关索引；更新索引列或删除任务时也一样。因此索引会带来：

- 额外的数据库文件空间；

- 插入、更新和删除的维护成本；

- 更多需要理解和管理的表结构。
